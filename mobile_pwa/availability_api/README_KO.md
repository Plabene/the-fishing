# 월별 예약 조회 API

GitHub Pages 화면은 그대로 사용하고, Cloudflare Worker가 더피싱 및 확인된 선상24 선사의 공개 월 달력을 읽어 검증한 JSON만 반환합니다. PC 상시 실행은 필요하지 않습니다.

## 선상24 공개 예약표 연동 (2026-10-23 적용)

현재 웹은 `/v1/sunsang24/public-month?ship=1530&month=2026-10&fresh=1`을 사용합니다. 기존 Worker에 추가한 경로이므로 새 Cloudflare 계정이나 선상24 API 키를 발급할 필요가 없습니다. 중앙 JSON API를 활성화한 것은 아닙니다.

- `src/data/sunsang24PublicRoutes.json`에 실제 공개 예약표의 선박 ID로 검증한 **22개 홈페이지·35척**을 등록했습니다. PC 티어 21척 중 20척이 포함됩니다. 티어 목록의 가즈아호 `2068`은 주소 미확인입니다. 동일 이름의 가즈아호 `307`과 임의로 합치지 않습니다.
- PC `sunsang24_selector_strategy.py`의 `table.ship_unit`, 선박 ID, 어종, 운항시간, 잔여석 선택 방식을 참고했습니다. 홈페이지·조회 월·일정 ID가 맞아야 응답을 사용합니다. `남은자리`만 읽으며 예약 인원·정원에서 잔여석을 계산하지 않습니다. 전화예약 등 불명확한 상태는 미확인, 없는 요금은 null입니다. 공지 본문·예약자 명단은 결과에 포함하지 않습니다.
- 같은 홈페이지의 선박은 한 번의 조회 실행에서 응답을 공유합니다. 다음 조회 버튼에서는 새 원본을 읽습니다. 서버에는 잔여석을 저장하지 않습니다. 동시 요청은 최대 3개, 원본 요청은 분당 전체 120회·호스트별 12회 이내입니다. robots 정책만 최대 1시간 재사용하며 401/403/429에는 해당 호스트의 요청을 최소 10분 중단합니다. 다른 선사의 조회는 계속됩니다.
- 주소가 확인되지 않은 선박과 해당 월 일정이 확인되지 않은 선박은 성공/만석으로 처리하지 않습니다. 공식 예약 페이지 확인 안내를 표시합니다. 공개 표에 없는 과거 일정·미등록 일정은 복원하거나 추정하지 않습니다.
- `/health`의 `platforms.sunsang24=public_homepages`, `sunsang24PublicShips=35`가 적용 여부를 표시합니다. `sunsang24CentralApi=permission_required`는 아래 중앙 API의 별도 상태입니다.

실측과 테스트 결과는 [통합 기록](../INTEGRATION_SUNSANG24_KO.md#공개-예약표-연동-추가-2026-10-23)을 참고하세요.

## 선상24 API 연동 진단과 신청

아래는 공개 예약표 연동 전의 진단과 **중앙 API** 신청 안내입니다. 현재 웹은 위의 공개 예약표 경로를 사용합니다. 중앙 API는 여전히 비활성 상태이며, 별도의 공식 API 연동이나 확인되지 않은 선박의 조회 확대가 필요할 때 아래 안내를 참고합니다.

초기 확인에서 선상24 월조회가 비어 있는 직접적인 원인은 **의도적으로 꺼 둔 중앙 API 연동**이었다. 선박 목록 380개와 PC 티어 21개를 가져오는 것과 새로운 일정·잔여석을 수집하는 것은 별도 기능이다. 현재 전체 목록은 PC 공개 자료이며 자동 갱신하지 않는다.

| 확인 대상 | 실제 결과 |
| --- | --- |
| 웹 `src/platforms.ts` | `SUNSANG24_LIVE_ENABLED=false` |
| 웹 `Sunsang24Api.readMonth` | 원본/API 요청 전에 `PERMISSION_DENIED` 반환 |
| 서버 `Sunsang24Service` | 생성자 기본 `enabled=false`, Worker에서도 활성화하지 않음 |
| 운영 `/health` | HTTP 200, `ready=true`, `platforms.sunsang24=permission_required` |
| 운영 `/v1/sunsang24/month?area=500&month=2026-10&fresh=1` | HTTP 200, 응답 본문 `status=PERMISSION_DENIED`, 일정 0개 |
| `https://api.sunsang24.com/robots.txt` | HTTP 200, `User-agent: *`, `Disallow: /` |

`PERMISSION_DENIED`는 이 앱에서 만든 상태이며 이번 요청에 선상24가 HTTP 403을 반환했다는 뜻이 아니다. 이전에 사용자가 ‘허가·별도 API 없음 — 가능한 통합부터 진행’을 선택하여 수집을 비활성화했다. 반복 클릭, 앱 재설치, Cloudflare 계정 재발급으로 풀리는 문제가 아니다. robots.txt 자체는 API 키 신청서가 아니며, 키 필요 여부나 계약 조건을 알려주지도 않는다.

### 별도 서버나 API 키가 필요한가

더피싱에 연결한 것은 **본인 Cloudflare 계정에 배포한 중계 API**다. 더피싱 운영사에서 공식 API 키를 발급받은 것이 아니다. 기존 Worker에 플랫폼별 경로를 추가하는 구조이므로 선상24 때문에 Cloudflare 계정이나 서버를 먼저 새로 만들 필요는 없다. 다만 선상24가 허용하는 외부 연동 방식·인증 방법을 확인해야 한다.

공식 홈페이지와 운영사 안내에서 **공개 개발자 포털, 즉시 API 키 발급 메뉴, 외부 월별 잔여석 API 명세는 확인하지 못했다.** 비공개 제휴 API가 존재하는지는 운영사 답변이 필요하다. 선상24 연동 홈페이지 제작 상품은 안내되어 있지만, 이 상품이 타사 통합 웹사이트용 API 사용 권한을 포함한다는 근거는 확인되지 않았다.

### 1. 공식 문의 창구

[선상24 홈페이지](https://www.sunsang24.com/)의 마케팅/제휴 문의는 **live@sandago.co.kr**, 고객센터는 **041-547-4401**, 안내 운영시간은 **10:00~18:00**다. [운영사 제휴 안내](https://www.sandago.co.kr/v2/)에서도 같은 연락처를 확인했다. 일반 선박별 문의가 아닌 플랫폼 운영사에 외부 데이터 연동을 문의한다. 이 작업에서는 이메일이나 문의를 대신 발송하지 않았다.

### 2. 보낼 문의문 예시

> 제목: 외부 예약조회 웹사이트의 선상24 API 연동 문의
>
> 안녕하세요. https://plabene.github.io/the-fishing/ 에서 선박별 월간 출조 일정과 잔여석을 확인하는 웹사이트를 운영하고 있습니다.
> 선상24 선박의 고유 ID, 선박명, 출항지/지역 코드, 출조 날짜·시간, 어종, 예약 상태, 잔여석, 공식 예약 URL을 외부 웹사이트에서 읽기 전용으로 표시할 수 있는 공식 API 또는 제휴 연동 방법이 있는지 문의드립니다.
> 사용자가 조회 버튼을 누를 때 최신 자료를 확인하고, 예약·결제는 선상24 공식 페이지로 연결하려 합니다. 예약자 정보나 회원정보는 요청하지 않습니다.
> 공식 연동이 가능하다면 신청 자격, 신청/계약 절차, 비용, API 문서, 인증키 또는 OAuth 발급 방법, 허용 호출량, 저장·재표시 조건, 출처 표시 방식, 도메인/IP 등록 필요 여부를 안내 부탁드립니다.
> 프런트엔드는 GitHub Pages, 중계 서버는 Cloudflare Workers입니다. 이 환경에서의 호출이 가능한지도 확인 부탁드립니다. 현재 API 호스트의 자동 수집 제한이 있어 승인 전 실시간 수집은 비활성화한 상태입니다.

### 3. 답변에서 받아야 할 것

1. 이 웹사이트에서의 외부 표시 허용 여부와 승인 범위. 선박 목록 갱신, 월별 일정·잔여석 조회를 각각 확인한다.
2. 공식 API 기본 URL, 허용 경로·메서드·매개변수, 테스트 환경과 응답 예제. 기존 PC 내부 호출 경로가 그대로 허용된다고 가정하지 않는다.
3. 인증 방식: API Key, Bearer 토큰, OAuth 등 운영사가 지정하는 방식 및 발급/만료/갱신 절차. 키 없이 승인된 공개 경로를 쓰는 방식이라면 그 범위를 문서로 확인한다.
4. 분·일 호출 한도, 동시 요청 수, 캐싱 조건, 전체 페이지 조회 방식, 실패 시 재시도 정책.
5. 지역 코드·선박 ID·일정 ID의 의미와 변경 정책, 잔여석 미제공/예약 마감/취소 상태 구분.
6. 도메인·출발 IP 등록, 요금, 출처/예약 링크 표시 조건. 비용과 발급 소요 시간은 아직 확인되지 않았다.

### 4. 승인·명세를 받은 후 구현과 설정

- `availability_api/sunsang24.ts`를 승인된 API의 경로·인증·응답 구조에 맞춘다. 현재 모듈은 PC에서 분석한 형식을 기반으로 한 비활성 구현이며, 키를 넣는 것만으로 작동하는 공식 SDK가 아니다.
- 인증키가 필요한 경우 서버의 Secret에 보관한다. 예를 들어 코드에서 `SUNSANG24_API_KEY`라는 바인딩을 사용하도록 구현한 뒤 다음 명령으로 입력한다. 명령은 키 보관 절차이며 현재 비활성 연동을 켜는 명령이 아니다.

```powershell
Set-Location D:\the-fishing
.\mobile.cmd exec wrangler secret put SUNSANG24_API_KEY
```

입력 프롬프트에 키를 입력하고 GitHub, 프런트엔드 `VITE_` 변수, 채팅에 키를 붙여넣지 않는다. OAuth 방식이면 운영사 명세에 따른 별도의 토큰 발급·갱신 구현이 필요하다. Secret 처리 방식은 [Cloudflare 공식 안내](https://developers.cloudflare.com/workers/configuration/secrets/)를 따른다.

- Worker 환경 타입과 생성자에 인증 설정을 연결하고, 허용 호출량·타임아웃·상태 해석을 적용한다. 승인 전 플래그만 `true`로 바꾸지 않는다.
- 검증용 선박 1척/1개월부터 원본 공식 페이지와 날짜·어종·잔여석을 비교한다. 전체 페이지 누락, 동명 선박, 월 변경, 401/403/429, 부분 실패도 확인한다. 예전 좌석을 현재 좌석으로 재사용하지 않는다.
- 통과 후 서버를 배포하고, 클라이언트의 실시간 지원 상태와 `/health` 표시를 함께 갱신한다. 기존 GitHub Pages 주소와 Worker 주소를 유지할 수 있다.

```powershell
.\mobile.cmd test --maxWorkers=2
.\mobile.cmd run api:check
.\mobile.cmd run api:deploy
$env:PWA_BASE='/the-fishing/'
.\mobile.cmd run build
```

서버 배포와 별개로 프런트엔드 수정은 기존 `main` 브랜치의 GitHub Pages 배포를 거친다. 운영 API와 실제 모바일에서 한 번 더 비교한 뒤 완료로 판단한다.

### 승인된 연동이 제공되지 않는 경우

현재 가능한 방법은 저장된 선박 목록·티어 검색, 공식 예약 페이지에서 최신 좌석 확인, 사용자가 가진 조회 결과 JSON 가져오기다. 수동으로 가져온 결과는 과거 조회 자료로 구분되며 실시간 잔여석을 대신하지 않는다. 공개 API 발급 절차를 확인하지 못한 상태에서 존재하지 않는 신청 메뉴나 키를 안내할 수는 없다.

## 사용

기본 API가 연결되어 있으므로 **조회 API 사용 → 실시간 월 조회**를 누릅니다. 과거에 직접 연결을 해제했거나 다른 배포를 쓰려면 **조회 API 연결**에서 주소를 입력하고 **연결 확인 및 저장**을 누릅니다. 연결 확인은 `/health` 응답만 확인하며 원본 사이트 조회 성공 여부는 월 조회 결과로 판단합니다.

API 주소는 이 기기에만 저장합니다. 기존 선박 목록·티어·조회 자료는 유지됩니다. 예약 조회에는 선박 UID와 조회 월, 매번 새 조회를 요구하는 `fresh=1`, 물때 조회에는 조회 월만 전송합니다. 클라이언트에는 Cloudflare 토큰·공공데이터 인증키·계정 비밀번호·쿠키를 넣지 않습니다.

## 공개 선박 목록

`GET /v1/catalog?page=1`은 고정된 더피싱 공개 예약 목록의 해당 페이지에서 이름·UID·공식 URL·지역·항구만 반환합니다. 페이지는 1~100, 추가 매개변수·임의 URL·쿠키 전달은 지원하지 않습니다. GitHub Actions에서 원본 사이트로 직접 연결할 때 연결 시간 초과가 확인되어, 주간 목록 갱신은 이 API를 사용합니다.

별도 `catalog-v1` Durable Object에서 순차 처리·진행 중 중복 통합·최소 1초 간격·하루 최대 100회 원본 요청을 적용합니다. 공개 목록 메타데이터만 24시간 저장하며 확인 시각을 유지합니다. **예약 잔여석은 이 캐시에 포함하지 않고 기존대로 매번 새 조회합니다.** HTTP 오류·리디렉션·형식 오류·시간 초과는 재시도 없이 10분 중단합니다. 원본 HTML과 연락처는 반환하지 않습니다. GitHub의 수집기는 다시 UID·공식 URL·건수·페이지·확인 시각을 검증한 후 목록에 병합합니다.

## 보령 물때

`GET /v1/tides?month=YYYY-MM`은 국립해양조사원의 [조석예보(고, 저조)](https://www.data.go.kr/data/15156018/openapi.do)에서 보령(DT_0025)의 일별 고조·저조를 반환합니다. PC와 동일하게 전월 말일·다음 월 첫날도 포함해 하루 경계의 조차를 계산합니다. 최대 3개 일별 요청, 요청 시작 간격 300ms, 일별 응답 제한 20초, 전체 일일 처리 예산 2,000회입니다. 같은 월 요청을 합치고 월·일별 성공 자료를 12시간 보관하며 인접 월의 겹치는 날짜를 재사용합니다. 인증·통신 오류 시 중단하고 60초 대기합니다.

기존 예약 조회와 다른 Durable Object 이름 `tides-v1`을 사용하므로 선박 조회 처리량·대기열을 공유하지 않습니다. `/health`의 `tidesReady`는 서버 인증키 설정 여부이며 실제 조회 성공 여부는 물때 응답에서 확인합니다. 브라우저는 **물때 새로고침**을 누를 때만 요청하고 수신 자료를 기기에 보관합니다. 실패 시 기존 자료를 보존합니다.

서버 인증키는 `KHOA_TIDE_API_KEY`라는 Cloudflare secret으로 설정합니다. 최초 설정/갱신은 저장소 루트에서 아래 명령의 입력 프롬프트를 이용하며 키를 파일·명령행 인자·Git에 넣지 않습니다. 이 배포는 기존 PC 자격 증명 저장소의 키를 비밀 입력으로 전달했습니다.

```powershell
.\mobile.cmd exec wrangler secret put KHOA_TIDE_API_KEY
```

## 본인 계정 배포

저장소 루트 `D:\the-fishing`에서 실행합니다.

```powershell
.\mobile.cmd exec wrangler login --device --browser=false
.\mobile.cmd run api:check
.\mobile.cmd run api:deploy
```

최초 로그인 또는 인증 만료 시 명령이 출력한 Cloudflare 로그인 URL에서 일회용 코드를 입력하고 사용자가 직접 승인합니다. 코드는 5분 뒤 만료되므로 만료되면 로그인 명령을 다시 실행합니다. 이미 로그인되어 있으면 로그인 명령을 생략합니다. 배포 오류 `10034`는 계정 이메일 인증이 필요하다는 뜻입니다. API 토큰을 채팅이나 저장소에 붙여넣을 필요가 없습니다. 최초 배포 시 계정과 workers.dev 주소 설정을 요청할 수 있습니다. 생성된 `https://서비스명.계정명.workers.dev` 주소를 웹앱에 연결합니다. 모든 기기의 기본 주소를 바꾸려면 `src/data/apiEndpoint.json`의 `url`을 새 주소로 변경하고 GitHub에 반영합니다.

Cloudflare의 요금·사용량 한도는 본인 계정에서 확인하세요. 이 프로젝트는 별도 유료 요금제나 결제를 신청하지 않습니다.

GitHub Actions는 웹앱 테스트·API 빌드 검사·GitHub Pages 배포를 실행합니다. **Worker 소스 변경은 `api:deploy`로 별도 배포해야 합니다.** Cloudflare 계정 자격 증명은 GitHub에 추가하지 않았습니다.

## 조회 범위와 실패 처리

- API는 `/health`, `/v1/month?uid=숫자&month=YYYY-MM`, `/v1/tides?month=YYYY-MM`, `/v1/catalog?page=숫자` GET만 제공합니다. 임의 URL·헤더·예약 폼을 중계하지 않습니다.
- 원본 요청은 고정된 더피싱 상세 GET 및 발견·검증한 월 달력 POST만 수행합니다. 로그인·예약·결제·쿠키 전송이 없습니다. HTTP 리디렉션을 따르지 않습니다.
- 브라우저 호출 출처는 `https://plabene.github.io`로 제한합니다. CORS는 사용자 인증 수단이 아니므로 서버 측에서도 전역 처리량을 제한합니다.
- Durable Object 하나가 중복 요청을 합치고 최대 3척을 동시에 처리합니다. 원본 요청 시작 간격은 전체 방문자 합산 최소 1초, 각 요청은 10초 제한입니다. 신규 월 조회는 분당 최대 60건이며, 한도 갱신까지 5초 이내이면 잠시 기다려 긴 배치가 중간에 끊기지 않게 합니다. 대기는 최대 9건이며 초과 혼잡에서는 중단 상태를 반환합니다.
- 검증된 선박 UID·달력 경로·st_uid 메타데이터만 최대 256척, 24시간 보관합니다. 같은 날 다음 조회는 상세 GET을 반복하지 않고 달력 POST로 읽습니다. 기존 1시간 만료 항목은 다음 상세 조회에서 새 기간으로 저장합니다. 응답 검증 실패 시 메타데이터를 지워 다음 수동 조회에서 상세 페이지를 다시 확인합니다. 주소 캐시 기간은 잔여석 유효기간과 별개입니다.
- 예약 성공 응답은 캐시에 저장하거나 재사용하지 않습니다. 과거 Durable Object의 `month:*` 키가 남아 있어도 읽지 않습니다. 진행 중인 동일 요청만 합치며, 완료 후 재조회는 원본 월 달력을 다시 읽습니다. 이전 클라이언트의 `uid`·`month` 요청도 서버에서는 새로 읽습니다.
- 웹앱은 `/v1/month?uid=…&month=…&fresh=1`을 `cache: no-store`로 호출합니다. 성공 응답에 `fresh=true`가 없거나 `cached=true`이면 좌석을 표시하지 않습니다. 기기의 예전 API 캐시는 읽지 않습니다. 최대 3개 API 요청을 병렬 처리하고 이번 조회에서 완료된 결과부터 달력·날짜 상세에 반영합니다. 인원·어종·티어 조건은 새로 받은 전체 출조 자료에 적용합니다. UI의 10분 경과 표시는 자료 노후 상태를 알리는 기준이며 응답 재사용 기간이 아닙니다.
- 401/403/429·보안 화면에서는 10분간 중단합니다. 네트워크·시간 초과에서는 30초간 중단합니다. 예약 성공·일반 실패 결과를 저장하는 캐시는 사용하지 않고 전역 접근 제한 대기 상태만 유지합니다. 실패를 빈 달력 성공으로 표시하지 않습니다.
- 응답 선박·월·숫자 잔여석·관측 시각은 서버와 웹앱에서 검증합니다. 실패한 선박의 기존 기기 자료는 백업용으로 보존하되 현재 조회 화면에는 표시하지 않습니다.
- 출조명 `trip`과 함께 `speciesKey`·`species`를 반환합니다. PC 파서처럼 가격 요소를 제거하고 상품 링크의 텍스트는 유지합니다. 동일 예약 버튼이 여러 번 있으면 출조 상품 정보가 더 많은 영역을 우선합니다. 예약 링크를 실행하지 않습니다. 기존 클라이언트는 추가 필드를 무시하고 사용할 수 있습니다.

실제 운영 조회는 테스트에서 자동 실행하지 않습니다. 자동 테스트는 HTTP 응답을 모의 처리합니다. 로컬 API가 필요하면 `api:dev`로 시작하며, 실제 원본 요청은 직접 `/v1/month` 또는 인증키를 설정한 `/v1/tides`를 호출할 때만 실행됩니다.
