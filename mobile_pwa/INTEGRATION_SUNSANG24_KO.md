# 선상24 통합 기록

## 분석 및 적용 범위 (2026-10-23)

수정 전 Git 기준점은 `45577f9`, 로컬 보존 브랜치는 `backup/pre-sunsang24-20261023`이다. 원본 Python 프로젝트는 수정하지 않는다.

더피싱은 TypeScript/Vite 정적 PWA, IndexedDB 개인 설정, Cloudflare Worker/Durable Object 조회 API 구조다. 선상24 PC의 `sunsang24_central_search.py`, `sunsang24_monthly.py`, `sunsang24_filter_schema.py`, `geographic_labels.py`를 분석했다. 중앙 월 조회는 정확한 하위 지역 ID 하나씩, 날짜 범위와 페이지 번호로 요청한다. total·고유 일정 수·날짜·지역이 일치해야 완전한 결과다. 선박별 선사 페이지 요청으로 바꾸지 않고 이 계약을 별도 TypeScript 모듈로 옮긴다.

선상24 공개 배포 카탈로그는 380개, 실제 지역 코드가 보존된 PC 카탈로그는 376개다. 나머지 4개는 검증된 선사 링크와 팔포항 정보가 있으나 중앙 지역 코드는 없다. 기존 더피싱 목록에도 있던 선상24 외부 링크 4개는 정확한 이름·출항지·동일 선사 URL·PC 식별자 연결 근거로 기존 UID를 유지한다. 플랫폼 간 동일 선박은 이름만으로 합치지 않으며 예약정보·링크·일정 ID를 각각 유지한다.

## 지역 설계 대안

1. 원본 명칭 그대로: 가장 단순하지만 충남/충청남도, 보령/보령시가 갈라진다.
2. 모든 명칭의 접미사 제거·유사문자 매칭: 편리하지만 인근·섬·복수 지역을 잘못 합친다.
3. **출처를 보존한 명시적 정규화(선택)**: 검증한 시·도 별칭과 지역 코드/이름 쌍을 사용하고, 섬·항구는 상위 지역과 실제 출항지 근거가 있는 규칙만 적용한다. 불명확한 복수 지역은 원문을 남기며 미확인 항구를 만들지 않는다. 조회 시 고정 사전 조회이므로 추가 네트워크가 없다.

선상24의 `태안인근`, `보령인근`, `평택인근` 등은 실제 항구가 아니다. 항구 선택에서는 미확인으로 두고 원본 출항 구역으로 표시한다. 등록 지역 홍성/출항 구역 보령인근 같은 차이는 등록 지역으로 검색하고 양쪽 정보를 함께 노출한다. 정확한 항구 근거가 생기기 전에는 다른 시·군에 재분류하지 않는다.

더피싱의 경기도/인천 아래 오이도와 인천 항구는 같은 행정구역이 아니다. 항구 근거가 있는 항목만 경기도 시흥/인천으로 구분하고, 출항지 없는 인천 묶음은 분류를 유보한다. 개인 수정 자료는 원본 카탈로그 메타데이터로 덮어쓰지 않는다.

## 접근 상태

2026-10-23 `https://api.sunsang24.com/robots.txt`는 HTTP 200과 `User-agent: *`, `Disallow: /`를 반환했다. 기존 프로젝트 문서에도 이 제한과 과거 403이 기록되어 있다. 이용약관은 `https://app.sunsang24.com/customer/policy/service_termsofuse`에서 확인했다. 사용자는 허가·별도 API가 없음을 확인하고 가능한 통합부터 진행하도록 선택했다.

따라서 공개 선박 목록·필터·공식 페이지 연결을 제공하고 **선상24 실시간 자동 수집은 비활성화**한다. 현재 잔여석을 저장 자료로 대체하지 않는다. 중앙 조회 계약의 파서/페이지 검증/장애 격리는 비식별 테스트 응답으로 검증하며, 실제 API 계약 및 허용 범위를 재확인하기 전에는 활성화하지 않는다.

## 적용한 코드

- `src/data/sunsang24Fleet.json`: 공개 식별·지역·링크만 추출, 개인정보/설정/잔여석 제외.
- `src/platforms.ts`, `src/regions.ts`: 플랫폼 식별, 안전한 링크, 공통 지역, 기존 UID 호환.
- `src/defaultFleet.ts`, `src/importLegacy.ts`: 개인 선택·티어·삭제를 보존하며 목록 확장.
- `src/providers/sunsang24Api.ts`, `availability_api/sunsang24.ts`: 독립된 지역 단위 조회와 명시적 비활성 상태.
- 기존 화면/조회 조정 코드: 플랫폼 태그·필터, 오류 격리, 원본 예약 상태 표시.

Python 원본은 그대로 두었다. 정적 PWA와 기존 Worker 배포 구조를 유지했으며, 새 데이터베이스나 로그인 기능을 만들지 않았다. `scripts/import-sunsang24-catalog.py`는 공개 식별 필드만 추출하는 재현 가능한 로컬 이관 도구다.

## 식별·예약 데이터와 오류 처리

선상24 신규 UID는 `sunsang24:ship:<ship_no>`, 일정 ID는 `sunsang24-schedule-<schedule_no>`다. 일정 번호가 없으면 PC와 같은 선박·날짜·출항시각·어종·요금 조합을 해시한다. 더피싱 UID/일정 ID는 그대로 유지한다.

동명 선박은 출항지·지역이 같아도 동일 선박 후보일 뿐이며 자동 병합하지 않는다. 플랫폼별 행·잔여석·상태·링크를 별도로 유지한다. 같은 선사의 URL 하나를 두 선박이 공유하는 경우도 있으므로 URL만으로 병합하지 않는다. 이미 저장된 선상24 외부 링크 4개만 PC의 명시적 선박 ID 연결과 정확한 이름·항구·URL이 모두 일치하여 기존 UID를 재사용한다.

공통 일정 모델에 원본 예약 상태와 날짜별 예약 페이지 URL을 추가했다. `remain_embarkation_num`에 실제 값이 없으면 `null`이다. 대기/마감이라는 이유로 0석을 생성하지 않으며, 양수 잔여석이 있더라도 예약 가능 상태가 아니면 인원 충족 결과에 넣지 않는다. 알 수 없는 상태·금액은 미확인이다. 0원도 무료라고 명시된 경우에만 0원으로 표시한다.

선상24는 별도 `sunsang24-v1` Durable Object로 분리했다. 실제 접근을 허용하는 변경을 하더라도 현재 지역 계층의 코드/명칭 검증 → 정확한 하위 지역 월 범위 → 모든 페이지/total/고유 일정 검증 순서를 거친다. 25초 제한, 1초 요청 간격, 분당 30개 원본 요청 예산, 최대 3개 대기 지역, 최대 20페이지/600개 일정 제한을 둔다. 한도를 넘거나 중간 페이지가 실패하면 일부 자료를 완전한 조회 결과로 표시하지 않는다. 더 큰 지역 결과의 날짜 분할 수집은 후속 작업이다.

401/403/429는 최소 10분 중단하며 다른 경로나 인증 수단으로 우회하지 않는다. 플랫폼별 중단과 예외를 격리하여 다른 플랫폼 결과는 계속 반영한다. 사용자의 전체 취소는 양쪽 조회를 중단한다. 잔여석은 저장 캐시로 대체하지 않으며, 클라이언트의 지역 응답 공유는 **조회 버튼 한 번의 실행 범위**에만 존재한다.
